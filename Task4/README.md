# Задание 4

- `nginx-rate-limit.conf` - rate limiter для API Gateway
- `nginx-circuit-breaker.conf` - circuit breaker для прокси к логистической службе

Оба конфига проверял локально в контейнере `nginx:1.27-alpine` с тестовым бэкендом.

## Rate limiter

Было: одна зона на всех, 100 r/s и `burst=200`, веб и мобилка никак не различаются.

Сделал две зоны: `web_api` на 50 r/s и `mobile_api` на 30 r/s с одного IP. Тип клиента берется из заголовка `X-Client-Type`, через `map` для запроса заполняется ключ только одной зоны (запросы с пустым ключом nginx не считает). Если заголовка нет, запрос идет под мобильный лимит: раньше мобильное приложение было единственным клиентом, и старые версии заголовок не присылают. `burst` примерно на секунду трафика, с `nodelay`, чтобы пачки запросов при открытии экрана не вставали в очередь. При превышении отдается 429.

Проверка: 10 потоков с одного IP, 5 секунд по 100 r/s. Для web прошло 300 запросов из 501 (50 r/s + burst), для mobile и без заголовка - 180 из 501 (30 r/s + burst).

Минус: заголовок можно подделать. Если это станет проблемой, можно развести клиентов по разным хостам или считать лимит по токену.

## Circuit breaker

- таймауты `proxy_connect_timeout`, `proxy_send_timeout`, `proxy_read_timeout` - 3 секунды;
- `max_fails=5 fail_timeout=30s` - после 5 ошибок nginx не ходит к логистам 30 секунд, потом пускает один пробный запрос, и если он прошел, трафик возвращается;
- ошибкой считаются таймаут, ошибка соединения и ответы 500/502/504 (`proxy_next_upstream`);
- fallback - локальный `server 127.0.0.1:8081 backup`, который отдает 503 с JSON и `Retry-After: 30`.

Backup-сервер нужен не только ради fallback: если в upstream один сервер, nginx игнорирует `max_fails` ([документация](https://nginx.org/ru/docs/http/ngx_http_upstream_module.html#server)). Проверил: без backup каждый запрос ждал 3 секунды и получал 504, цепь не размыкалась.

Еще добавил `zone`, чтобы счетчик ошибок был общий для всех воркеров, `proxy_set_header Host`, иначе внешнему сервису уйдет `Host: logistics_backend`, и `non_idempotent`, чтобы POST при таймауте тоже получал fallback.

Проверка: пока логисты отвечали через 10 секунд, первые 5 запросов получали fallback через 3 секунды, следующие сразу, без похода к логистам. Через 30 секунд, когда сервис ожил, запросы снова пошли к нему.

Из ограничений: nginx считает ошибки за окно `fail_timeout`, а не строго подряд, и 503 от самих логистов не считается ошибкой. Если добавить `http_503` в `proxy_next_upstream`, в разомкнутом состоянии клиент получает 502 вместо fallback.
